# AGENTS.md - GumaKidsPython 작업 지침

이 문서는 Codex가 `GumaKidsPython` 프로젝트에서 일할 때 가장 먼저 확인할 단일 기준 문서다.
진행 현황, 단기 TODO, 명령 예시처럼 계속 바뀌는 정보는 이 문서에 기록하지 않는다.

## 프로젝트 목적

- 초등학교 3학년 아이가 파이썬을 "문법 공부"가 아니라 "게임 업그레이드 놀이"로 배우게 한다.
- 전체 과정은 48챕터, 4개 시즌, 시즌당 12챕터를 기본 구조로 삼는다.
- 아이는 게임 전체를 처음부터 만들지 않는다.
- 웹버전에서 `upgrade_zone.py`의 작은 코드만 바꾸고, 결과를 브라우저 게임 화면에서 바로 확인한다.
- 앞으로 이 프로젝트의 기준 실행 환경은 웹버전뿐이다. `tkinter` 앱이나 시즌별 직접 파이썬 실행 버전은 다시 만들지 않는다.
- 교재와 앱에서는 "수정"보다 "업그레이드"라는 표현을 사용한다.

## 문서 역할

- `AGENTS.md`는 장기적인 작업 지침만 담는다.
- 특정 날짜의 구현 상태, 단기 TODO, 실행 중인 서버나 프로세스 정보는 기록하지 않는다.
- 새 산출물을 만들더라도 이 문서에는 반복해서 적용할 원칙만 추가한다.
- 현재 진행 상태가 필요하면 Git 이력, 이슈, 커밋 메시지, 작업 로그를 확인한다.

## 시즌 구성

| 시즌 | 챕터 | 게임 | 주요 학습 |
|---|---:|---|---|
| 시즌 1 | 1~12 | 보물 점수 게임 | 출력, 문자열, 숫자, 변수, 계산 |
| 시즌 2 | 13~24 | 괴수 러너 성장 게임 | 입력, 조건문, 비교, 논리 연산 |
| 시즌 3 | 25~36 | 몬스터 배틀 게임 | 반복문, 리스트, 딕셔너리, 게임 데이터 구조 |
| 시즌 4 | 37~48 | 미니 어드벤처 게임 | 함수, 클래스/객체 기초, 랜덤, 저장, 예외, 종합 |

## 웹버전 구조

프로젝트는 웹앱 중심으로 유지한다.

```text
server.py      # Flask 기반 웹 서버와 저장 API
web/index.html # 웹 학습 화면 구조
web/app.js     # 챕터, 코드 편집, 게임 로직, 저장 연동
web/style.css  # 웹 UI 스타일
Docs/          # PDF/PNG 강의자료
tools/         # 강의자료 생성 도구
```

작업 원칙:

- 웹 코드 편집기에 표시되는 `upgrade_zone.py`는 아이가 직접 보는 코드이므로 단순하고 읽기 쉽게 유지한다.
- 게임 로직은 `web/app.js` 안에서 브라우저로 동작해야 한다.
- 직접 실행용 `main.py`, `engine.py`, 시즌별 `games/` 폴더, `tkinter` 앱은 프로젝트 기준 구조에 포함하지 않는다.
- 한 챕터에서 새 개념은 하나만 다룬다.
- 시즌 1은 챕터 1~2만 1줄 수정으로 시작하고, 챕터 3부터 2줄 이상을 수정하게 한다. 챕터가 진행될수록 수정 줄 수를 늘려 챕터 12에서는 10줄 수준의 종합 업그레이드를 다룬다.
- 구조체에 해당하는 데이터 묶음은 Python에서는 딕셔너리, 리스트 안의 딕셔너리, 클래스/객체 순서로 쉽게 설명한다.
- 시즌 게임은 챕터가 진행될수록 화면 요소와 상호작용이 누적되어야 한다. 아이가 이전 챕터보다 게임이 확실히 커졌다고 느끼는 것을 우선한다.
- 시즌 2 러너/보스전의 주 장면은 Three.js/WebGL 기반 3D 캔버스로 보여주고, 보스전은 별도 화면으로 끊지 않고 같은 러너 무대에서 3D 카메라가 세로 주행 시점에서 가로 대전 시점으로 패닝되는 방식으로 유지한다.
- 시즌 2의 괴수 캐릭터는 3D 메시를 기준으로 만들고, CSS 2D 캐릭터는 WebGL 실패 시 백업 화면으로만 사용한다.
- 시즌 2 러너 구간은 Space 액션이 아니라 좌우 이동으로 아이템을 먹고 괴수가 성장/변신하는 조작감을 우선한다. Space는 보스전 타이밍 공격에만 사용한다.
- 시즌 2 캐릭터 변신은 `원숭이 -> 고릴라 -> 공룡`의 2단계 변신 흐름을 기준으로 삼고, 기본값은 200점 고릴라, 500점 공룡 변신으로 설계한다. 챕터24에서는 공룡 변신과 보스전의 불꽃/펀치 타격 이펙트가 분명히 보여야 한다.
- 시즌 2에서 캐릭터의 화면 크기는 단계별 상한을 두어 게임 화면을 가리지 않게 하고, 일정 점수/성장 기준을 넘으면 크기만 계속 키우기보다 다음 캐릭터로 변신시킨다.
- 시즌 2 러너 아이템은 같은 줄/같은 높이에 2개 이상 보이지 않도록 안전 간격을 유지하고, 이동 속도는 러너 초반에는 느리게, 보스 게이트에 가까워질수록 빠르게 만든다. 기본 플레이 타임은 보스전 진입 전 약 30초를 목표로 한다.
- 시즌 2 보스전은 플레이어 공격과 보스 공격을 분리된 턴으로 보여주며, 각 공격 전에 누구 차례인지 알려주는 팝업을 띄운다. 최종 승리 시 보스 소멸 연출과 승리 팝업을 보여준다.
- 챕터에서 새로 등장하는 게임 파라미터는 코드 편집기, 적용된 파라미터 UI, 실제 게임 로직에 모두 연결한다.
- 게임 화면에 보이는 수집 아이템, 위험 요소, 안내 문구는 이름표나 핵심 수치 중 하나 이상을 `upgrade_zone.py`에서 바꿀 수 있게 유지한다.
- 코드 주석은 아이가 이해할 수 있는 짧고 쉬운 문장으로 쓴다.
- 게임 기능을 추가해도 설치 부담을 만들지 않는다. 기본은 브라우저 기본 기능과 현재 웹 서버 구조다.

## 웹 학습 앱 원칙

- 강의자료, 게임화면, 파이썬 코드 화면을 동시에 볼 수 있는 구조를 우선한다.
- 강의자료는 항상 보이고, 코드 수정 후 실행 결과가 게임화면에 바로 반영되어야 한다.
- 기본 학습 화면은 가운데에 강의자료와 코드 편집기를 두고, 오른쪽 게임 화면은 모바일처럼 세로형을 우선하되 가독성을 위해 폭을 넓힌 portrait 비율을 사용한다.
- 전체 레이아웃에서는 코드내용과 게임화면을 가장 중요한 영역으로 보고, 코드내용이 포함된 가운데 세로줄에서는 코드 편집 영역이 약 70%를 차지하게 유지한다.
- 16:9 화면에서 페이지 자체가 세로 스크롤되지 않게 맞추고, 파일트리는 중요도가 낮으므로 접었다 펼 수 있는 보조 패널로 유지한다.
- 게임 패널에서는 제목/HUD와 시작/액션/다시시작 버튼을 가능하면 게임 화면 왼쪽 보조 레일에 두어 게임 보드의 세로 공간을 우선 확보한다.
- 시즌 1 보물 게임의 캐릭터와 아이템 배치도 세로형 보드를 기준으로 잡고, 아이템은 세로 레인처럼 읽히게 배치한다.
- 화면 분할은 아이가 헷갈리지 않도록 안정적인 기본 비율을 유지한다.
- 앱 크롬과 코드 편집기는 차분한 Dark 테마를 사용해 집중감을 준다.
- 강의자료 패널은 아이 눈에 잘 띄는 동화책처럼 밝고 알록달록한 스타일을 유지하고, 게임 화면은 밝고 아기자기한 색감을 유지한다.
- 게임 시작 안내는 짧은 중앙 연출로만 처리하고, 게임판 하단에 고정 안내/상태 텍스트 박스를 두지 않는다.
- 챕터 선택 UI는 학습 공간을 많이 차지하지 않게 작고 명확하게 만든다.
- 코드 저장은 챕터별로 분리해서 아이가 이전 작업을 잃지 않게 한다.
- 에러 메시지는 아이와 부모가 원인을 이해하고 다시 시도할 수 있게 짧고 친절하게 보여준다.

## 교재/PDF 원칙

- PDF는 공부 교재보다 게임 퀘스트북처럼 느껴지게 만든다.
- 웹앱용 강의자료는 가로형 PDF/PNG 페이지를 기준으로 제작한다.
- 한 챕터 강의자료는 5페이지 안팎을 기본으로 하며 최대 10페이지를 넘기지 않는다.
- 개념 설명이 필요한 챕터는 중간 설명 페이지를 추가할 수 있다.
- 따라 치는 코드는 가능한 1~3줄 수준으로 유지한다.
- 실제 게임 화면과 오늘 바꿀 코드가 명확히 연결되어야 한다.
- 숨겨진 구현 설명을 길게 넣지 않는다.
- 쉬운 코드 수정 미션만 넣지 말고, 문자열, 숫자, 변수 같은 파이썬 개념을 짧게 연결해 설명한다.
- 텍스트가 박스 밖으로 삐져나오지 않도록 여백과 글자 크기를 보수적으로 잡는다.
- 퀴즈는 초등 3학년이 말로 답할 수 있는 수준으로 만든다.
- 정답은 퀴즈 페이지에 바로 노출하지 않고 마지막 정답/해설 페이지에 둔다.

기본 챕터 흐름:

1. 표지: 오늘의 게임, 오늘의 업그레이드
2. 오늘의 코드
3. 코드가 한 일 또는 파이썬 개념
4. 바꿔보기 또는 Play 해보기
5. 업그레이드 미션과 퀴즈
6. 정답과 짧은 해설

## 검증 원칙

- 코드 변경 후에는 변경 범위에 맞게 문법 검사와 실행 확인을 한다.
- 웹앱을 바꾸면 `web/app.js` 문법 검사와 브라우저 렌더 확인을 우선한다.
- 저장 API나 배포 구성을 바꾸면 `server.py`, `Dockerfile`, `docker-compose.yml`도 함께 확인한다.
- 강의자료를 바꾸면 PDF/PNG를 다시 생성하고, 페이지 넘김과 텍스트 넘침을 눈으로 확인한다.
- Windows 터미널에서 한글 출력이 깨지거나 `UnicodeEncodeError`가 나면 코드 문제로 단정하지 말고 UTF-8 출력 설정을 고려한다.

## 작업 완료 절차

- 코드, 문서, 강의자료처럼 저장소에 남는 변경을 완료하면 사용자가 따로 지시하지 않아도 현재 PC에서 커밋하고 `git push`까지 진행한다.
- 푸시 뒤에는 `ssh HomeServer`로 홈서버에 접속해 `D:\TheGumaLab\pull_update.bat GumaKidsPython`으로 최신 내용을 반영한다.
- Docker 반영이 필요한 변경이면 `gumakidspython_app` 컨테이너를 재시작하거나, 빌드가 필요한 경우 compose 빌드를 포함해 재기동한다.
- 홈서버 반영 뒤에는 홈서버의 최신 커밋, 컨테이너 상태, 필요 시 HTTP 응답을 확인한다.
- 단순 조사나 답변처럼 저장소 변경이 없는 작업은 푸시와 배포를 생략한다.

## 웹앱 원칙

- 웹앱은 GumaKidsPython의 유일한 기준 실행 환경이다.
- 저장 API는 아이의 챕터별 진행 데이터를 안전하게 보관해야 한다.
- 저장 데이터 구조를 바꿀 때는 기존 저장 파일과의 호환성을 검토한다.
- 배포 관련 설정은 홈서버와 로컬 실행 환경을 모두 고려한다.

## 주의 사항

- 아이가 실수해도 다시 실행하면 된다는 느낌을 유지한다.
- 게임의 난이도보다 학습 개념의 명확성을 우선한다.
- 부모가 복구할 수 있는 경로를 항상 남긴다.
- 커밋이나 압축본에는 실행에 불필요한 `__pycache__` 폴더를 포함하지 않는다.
- 관련 없는 파일이나 사용자 변경은 되돌리지 않는다.
